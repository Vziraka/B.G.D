# Clause-accountable desk conversation candidate — 27 September 2026

## Decision boundary

The first Qwen3.5-4B integrated profile passed 30/30 development requests but failed its one sealed 100-request evaluation (42/49 consequential, 39/51 ordinary). Phi-4-mini-instruct Q4_K_M then scored 23/30 on the original development set, including a direct negation inversion and an unbound “yes” becoming `follow me`. Neither profile may be the default interpreter. Keep model use opt-in, desk-only and simulation-only. Do not use the consumed 100 requests for tuning or claim a new held-out result from them.

The next candidate retains the Qwen3.5-4B model but changes the **interpretation boundary**, not aircraft authority. A local language model still maps open-ended natural requests to follow, find, count and status intentions. A small, independent request-policy check must reject an affirmative unavailable capability or attempt to bypass review anywhere in the request before a partial model plan can become a proposal. Explicit negation must never become a positive action. An ambiguous reference or a request whose action/target cannot be grounded must ask for clarification. The review card and one-use confirmation remain separate from model output.

## Implementation shape

1. Account for every explicit requested clause. If an affirmative clause asks to move the fixed camera/aircraft beyond its current view, record/share/save media, access files/secrets/terminal/network, spend money, alter identity data, or skip confirmation, refuse the **whole** request. Do not quietly keep an otherwise supported clause. A negated unavailable action followed by a clear status request should still answer status, as the existing flight-polarity behavior does.
2. Keep the deterministic check focused on capability and authority boundaries. It is a guard, not a growing replacement for natural-language understanding. Use generic patterns/relationships and conservative clarification for uncertain polarity. Distinguish a question *about* pending confirmation from an instruction to omit it. Preserve the fast Stop path, and do not make Stop wait on the local model.
3. In the model profile, state action meanings precisely: following means maintaining the selected target within the current fixed view, finding means locating a target, counting retains the named category, and status includes current and last mission state. Do not invent a prerequisite find, change a named count target to people, treat absent context as visual grounding, or reinterpret a status question as scouting. Preserve full target descriptions and ordered genuinely requested multi-step intentions. Normalize only wording that has the same downstream executor effect; do not waive a dropped clause or changed target as a synonym.
4. Keep a single bounded local model call per request and the existing strict JSON validator. New guard/normalization code should be cheap compared with inference and must not add an unmeasured second LLM call. Direct model output remains `DIAGNOSTIC_ONLY`; only the authenticated exact proposal can be confirmed for desk simulation. Do not enable the model by default or deploy to the Pi during this candidate stage.
