# Issue12 iPhone route recheck — September 10, 2026

**Later owner direction, September 10:** remote Mac access is the expected native-iPhone build direction; **no provider is selected or purchased**. Q72's legitimate personal signing/refresh through Windows remains an evaluation path, not a demonstrated deployment. A hosted runner or remote Mac service is a candidate delivery method subject to compatibility, privacy, maintenance and cost review. No account, device, installation, upload, subscription or purchase was used in this assessment. This report applies the later [v1 contract](../phone-drone/interaction-contract.md); older speaker-verification and biometric-before-launch language in Q72 research is historical.

## Current source-backed findings

| Area | Current documented fact | B.G.D consequence / evidence still missing |
|---|---|---|
| Build host | Apple publishes supported macOS, Xcode, SDK and device combinations in its [Xcode system requirements](https://developer.apple.com/xcode/system-requirements/). | Windows can host this simulator and source editing. A real native build still needs a compatible Mac toolchain. Pin an available supported Xcode/runner combination against the actual installed phone OS during the authorized build spike; no build has run. |
| Personal signing | Apple documents seven-day Personal Team profiles, three installed apps per device and periodic rebuilding/reinstallation in its [developer account overview](https://developer.apple.com/help/account/basics/about-your-developer-account). | Preserve the accepted weekly maintenance tradeoff. App expiry must revoke sessions and leave independent radio authority intact; it cannot be assumed away. |
| Windows install route | The [AltStore Windows guide](https://faq.altstore.io/altstore-classic/how-to-install-altstore-windows) documents Apple software dependencies, account authentication, computer/device trust and Developer Mode. [AltStore refresh documentation](https://faq.altstore.io/altstore-classic/your-altstore) says apps expire after seven days; background renewal is attempted, not guaranteed. | Compile/package/personal re-sign compatibility for this app, exact entitlements and the owner's phone remain untested. Do not install dependencies or enter credentials based on this paper assessment. This third-party route is not an Apple end-to-end endorsement. |
| Private builds and cost | [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) currently lists 2,000 included monthly minutes and 500 MB artifact storage for Free, with OS-dependent consumption/cost; its baseline macOS rate is $0.062/minute outside applicable allowances. | A $0 service-cost proposal is conditional on the actual account quota, runner and storage usage. Before an authorized upload, configure and verify spending stops; keep the repo private, exclude credentials/biometrics/recovery secrets, and do not assume 2,000 macOS minutes are free. |
| Audio lifecycle | Apple's [record category](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record) documents background/locked recording with the audio background mode and microphone permission, with interruptions still possible. [Interruption](https://developer.apple.com/documentation/avfaudio/handling-audio-interruptions) and [route-change](https://developer.apple.com/documentation/avfaudio/responding-to-audio-route-changes) notifications expose calls and device changes. | Native audio is a supported building block. The v1 policy still closes a speech window on lock/background suspension, focus loss, calls or route changes; it never automatically resumes captured audio. Background capability is not permission for always-listening operation. |
| EarPods control | [MPRemoteCommandCenter](https://developer.apple.com/documentation/mediaplayer/mpremotecommandcenter) exposes remote events from accessories/system controls, principally media commands. | This does **not** establish raw press-down/release delivery for USB-C EarPods in every lifecycle state. Test deliberate hold semantics on the exact phone/headset. The approved on-screen hold is the simulator/fallback route; it does not prove pocketed parity. |
| Offline speech | Apple says [requiresOnDeviceRecognition](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition) prevents network audio only when the recognizer also supports on-device recognition. | Check capability for the selected locale/model and fail closed if unavailable; do not fall back to cloud recognition. Speech selects an action; the current onboard face/liveness session supplies authority. |
| Local Wi-Fi | Apple's [TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) requires local-network consent and explains denial/revocation. Initial background access while permission is undetermined is denied without showing the prompt; the iOS simulator does not model this privacy gate. | Obtain permission in a foreground device test, then test denied/revoked access. Native reconnection must not restore a launch, verification or command session. Actual mutually authenticated command/media channels, Wi-Fi capacity/range, video latency and power are unimplemented. |

Apple documentation's Markdown endpoints were read directly when the browser tool returned JavaScript shells. All links above were rechecked September 10; source documentation establishes API capabilities, not this application's behavior.

## Concrete next integration sequence

1. Keep the desktop demonstration actuator-free. Reuse its protocol and rejection fixtures when implementing a transport adapter; add mutually authenticated sessions and a separately encrypted, ephemeral preview channel before any real-camera integration. Simulator pairing markers are not cryptographic credentials.
2. Prepare the native foreground controller around on-screen launch/speech holds, exact request acknowledgments, preview guidance and lifecycle invalidation. Preserve EarPods/pocketed operation as an explicit actual-device gate, not an omitted feature.
3. With separate owner authorization for private source upload, service/account setup, device trust and installation, run the native compile/package/install/renewal spike. Use no biometric material. Confirm real local-network denial/revocation, offline speech capability and EarPods events before promising deployment.
4. Real camera/face/liveness, encrypted ownership persistence, anti-rollback, hardware power/thermal, SITL/FC authority enforcement and qualified recovery require their own subsequent evidence. The present simulator cannot satisfy those gates.

No new hardware or paid signing route is selected. This continuation fits Issue12; it does not need a separate future-outcome ticket merely to track the next adapter step.
