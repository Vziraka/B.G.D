## Source principles and limits

- OWASP says throttling design must balance the failure threshold, observation window and delay against usability; malicious attempts can deny access to legitimate users. Its web-login examples inform the tradeoff, not a selected Windows biometric policy. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling)
- NIST SP 800-63B-4 specifies, within its framework, five consecutive biometric failures (ten with qualifying presentation-attack detection), then at least thirty seconds **before each subsequent attempt**, with eventual disabling at overall limits. It also prohibits voice biometric comparison and requires biometrics alongside a physical authenticator. **B.G.D does not claim NIST compliance; face plus voice are not two different factor categories.** Adopting a delay alone cannot inherit the framework's assurance. [NIST biometrics](https://pages.nist.gov/800-63-4/sp800-63b.html#use-of-biometrics)
- OWASP recommends bounded authorization windows chosen around real user behavior, unique authorization per operation, and a final execution check. It prescribes no universal sixty-second window. [OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html#29-authorization-credentials-should-only-be-valid-during-a-limited-time-period)
- NIST's saved-recovery-code guidance calls for secure offline keeping, hashed verifier storage, throttled checking, and invalidating a used code while issuing a replacement. This supports replacement as a security principle, not a ready-made crash-safe implementation for B.G.D. [NIST saved recovery codes](https://pages.nist.gov/800-63-4/sp800-63b.html#saved-recovery-codes)
- Microsoft supplies an action-consent verification API with a result distinguishing successful verification from failure. Its examples verify the logged-on user and use a window-bound interop API for desktop apps. The project must still establish designated-owner binding and offline behavior; opening a prompt is not successful verification. [Microsoft UserConsentVerifier](https://learn.microsoft.com/en-us/uwp/api/windows.security.credentials.ui.userconsentverifier?view=winrt-26100)

## 1. Repeated failed checks

**Suggested initial project policy for evaluation:** after five consecutive rejected face-and-voice authorization requests, wait thirty seconds before the next request; while the failure streak continues, impose the delay before **each** further request. A successful complete check resets the streak. Preserve enrollment; the delay never grants approval or demands re-enrollment. These numbers and reset semantics remain unapproved and unvalidated.

The simpler alternative, thirty seconds after every batch of five failures, permits roughly five times the sustained attempt rate when capture time is negligible. Neither fixed policy establishes adequate attack resistance; the actual full-request rate and spoof success matter. A finite increasing delay could slow persistent attacks further, at the cost of longer legitimate waits. Do not silently add permanent disabling or a Windows-only bypass: Q61 chose a temporary pause, and Q20–Q23 define the separate recovery path.

**Concrete progressive alternative requested during research:** after the fifth consecutive rejected request, wait thirty seconds; after the sixth, sixty; after the seventh, 120; after the eighth, 240; after the ninth and every later rejection, 300 seconds. A complete successful check resets the streak. This is a project proposal, not a sourced safe threshold. It lowers the continuing attempt rate compared with fixed thirty-second waits, but a person deliberately provoking failures can leave the owner waiting up to five minutes for each next attempt. The cap prevents an ever-growing pause, not repeated denial of service. Requests refused during an existing pause should not extend its deadline. Persist the streak across restart; no hidden permanent cutoff. The parent may recommend this explicit schedule instead of the fixed starting option, provided the added waiting burden is presented and accepted. Actual thresholds must be frozen before evaluation and revisited if owner usability or security evidence fails.

**User consequence to confirm:** a string of mistakes can make every later retry wait, but does not erase the profile. Show remaining wait and practical camera/audio troubleshooting without promising an attacker cannot induce delays.

Engineering must define and validate:

- One counted attempt is one completed authorization request rejected by the gate, even if processing stops after a failed component; frames or audio chunks are not separate attempts. A caller must not obtain unlimited identity comparisons inside an “incomplete” request.
- Distinguish no-input/cancellation/device faults from an evaluated rejection while ensuring cancellation, parallel requests, alternate entry points and app restart cannot bypass attempt controls. Failed checks remain failed evaluation trials even if a retry succeeds.
- Persist the required delay/counter safely across restart; handle clock changes, sleep and corrupt state without either resetting protection or unexpectedly imposing permanent lockout. Choose reset/observation/escalation rules from measured owner friction and attack exposure, not user guesses.
- Recovery-code guessing needs its own controls. A biometric cooldown must not remove the already approved code-plus-fresh-owner-Windows recovery option, but that path cannot become unlimited code guessing or direct ordinary-action approval.

## 2. An incomplete check must expire

**Suggested project starting value: sixty seconds absolute from initiating a normal interactive face-and-voice verification request**, without extending the window whenever new input arrives. At expiry, deny that request, discard all partial successes and require a fresh full check; retain enrollment. Cancellation, device loss or restart already require fresh verification under Q38 and can end it sooner.

This is a generous stalled-request limit to validate, **not** a sixty-second normal-performance target, an unlocked session, or an in-flight rule. The approved ten-second successful-check target remains. One authorized action still cannot authorize another under Q41. Enrollment and recovery have different workflows; do not impose this normal-check timeout on saving a recovery code or replace Q60's separate five-minute enrollment target.

**User consequence to confirm:** stepping away for a minute means starting the check again, not re-enrolling. Engineering owns timer start, late asynchronous results, sleep/account changes, challenge freshness, and the permitted interval between completion and the one authorized action. The last interval is distinct and must not silently become a reusable sixty-second approval.

## 3. Replace a code after successful recovery

**Recommend one-use recovery codes at successful recovery completion**, with a fresh code saved for the next emergency. This reduces continued usefulness of a previously exposed code. The inconvenience is updating the owner's offline copy whenever recovery succeeds.

Preserve the approved prerequisites: a valid code **plus fresh designated-owner Windows verification** permits lockout re-enrollment; replacing a lost code while biometrics work needs fresh face, voice and owner Windows checks and does not change enrollment. No code plus inability to pass either biometric still has no recovery route. Neither flow grants an ordinary protected action or arming permission.

**Proposed crash-safety acceptance outcome, not a chosen storage mechanism:** do not consume the old code merely on entry, Windows verification, or before a viable replacement is ready. Prepare and validate replacement enrollment, present the new code for secure offline saving and obtain saving confirmation before finalizing. Commit the new complete enrollment and new code state together with old-code invalidation. An interruption before commit retains the old committed profile/code; an interruption after commit retains the new committed pair and rejects the old code. A confirmed save cannot prove the human really preserved their copy; explain the loss consequence.

Engineering must choose durable transaction/restart handling, stop concurrent reuse, prevent obsolete backups from restoring consumed codes within the agreed threat model, and test interruption at every transition. Never add an indefinite old-code grace period, cleartext secret logs, automatic ownership reset or a promise of crash-proof storage. If the selected storage cannot satisfy the transition outcomes, recovery acceptance remains incomplete.

## Remaining decisions

Ask about the practical consequences—waiting during a continuing failure streak, restarting an abandoned check, and saving a replacement code—not arbitrary model thresholds or durability internals. The parameters here remain proposals. Trial design, consent, anti-spoofing, injection resistance and adequate security coverage remain independent acceptance work; throttling and expiry do not prove biometric security.
